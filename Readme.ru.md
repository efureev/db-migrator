# db-migrator

Миграции SQL для PostgreSQL: библиотека и CLI.

[English version](Readme.md)

```bash
go install github.com/efureev/db-migrator/v2/cmd/migrator@latest
```

```bash
migrator create 'add users table'   # создаст 20260819120000_add_users_table.{up,down}.sql
migrator status                     # что применено, что ждёт
migrator up                         # накатить всё ожидающее
```

## Чем отличается

**Миграция и запись о ней идут в одной транзакции.** Состояния «применена, но не
записана» этот инструмент породить не может.

**У каждой миграции есть чек-сумма её файла.** Правка уже применённой миграции
отвергается громко и до того, как что-либо запустится: базы, накатившие старый
текст, нового никогда не увидят. Сумма считается по нормализованной форме,
поэтому чекаут под Windows с `core.autocrlf=true` не выглядит правкой.

**`CREATE INDEX CONCURRENTLY` работает.** Миграция с директивой
`-- migrator:no-transaction` выполняется вне транзакции, по одному оператору.
Отправить файл целиком нельзя: PostgreSQL оборачивает многооператорный простой
запрос в неявную транзакцию, а внутри неё `CONCURRENTLY` падает. Такая миграция
записывается в два шага, поэтому падение между ними оставляет след, а не тишину.

**Сухой прогон говорит, что именно возьмёт каждый оператор.** Не «эта миграция
рискованная», а режим блокировки, таблица, её размер и переписывает ли она её:

```
  Plan  1 migration(s) up

    20260901130000_widen_status  transactional, 1 statement(s)
      ALTER TABLE orders ALTER COLUMN status TYPE text
        ACCESS EXCLUSIVE on orders (~8 900 000 rows), REWRITES THE TABLE
```

`--max-lock-level share-update-exclusive` превращает это в отказ — до первого
оператора. Миграция, которой тяжёлая блокировка действительно нужна, говорит об
этом в своём тексте: `-- migrator:lock-acknowledged access-exclusive`. Флага,
снимающего отказ, нет: решение принимается на ревью, в файле, а не тем, кто
держит деплой в три часа ночи.

Это эвристика по тексту оператора, а не планировщик: она не видит триггеров,
правил, наследования и очереди перед блокировкой. Её таблица правил проверяется
живым сервером, а это не то же самое, что проверяться самой собой.

**Долгая миграция говорит, что делает, пока делает.** Раз в 30 секунд второе
соединение читает собственные progress-вью PostgreSQL по бэкенду прогона и
пишет строку:

```
migrator: migration in progress  version=20260901130000 source=create_index
          phase=building index  relation=users  percent=30
          progress=12 400 000 of 41 200 000 blocks
```

Переписывание таблицы, бэкфилл и ожидание на локе не видны ни одной progress-вью
— для них строка собирается из `pg_stat_activity`: состояние, событие ожидания и
сколько идёт оператор. Час, который `CREATE INDEX CONCURRENTLY` молчит, — это час,
в течение которого никто не знает, жив ли он.

Комментарий идёт в stderr и потому не портит ответ под `--json`, а
`--progress-interval 0` его выключает. Нужно второе соединение: `FromDSN` и
`FromPool` его дают, `FromConn` — нет, и это обнаруживается, а не предполагается.

**Одновременные прогоны сериализуются advisory-локом PostgreSQL**, который
берётся до создания таблицы учёта. Лок сессионный, поэтому упавший процесс
освобождает его сам — чистить строку-замок руками не нужно.

**Разрушающие операции требуют трёх независимых вещей.** `wipe` нужен флаг
`--allow-wipe`, `--confirm <база>`, совпадающий с тем, что реально сообщает
соединение, и окружение, не являющееся production. `--yes` здесь никогда не
достаточно: он значит «не спрашивай», а `--confirm shop_dev` — «я знаю, что это
за база». Спасает именно опечатка в имени.

**Коды возврата различают «повторить» и «будить человека».**

## Как библиотека

Основной сценарий — сервис, который несёт миграции внутри своего бинарника:

```go
//go:embed migrations/*.sql
var embedded embed.FS

src, _ := fs.Sub(embedded, "migrations")

m, err := migrator.New(migrator.FromPool(pool), src,
    migrator.WithLogger(log),
    migrator.WithSchema("app"),
)
if err != nil {
    return err
}

report, err := m.Up(ctx)
```

`FromPool` удерживает одно соединение на весь прогон, а не маршрутизирует
операторы по пулу. Это не оптимизация: сессионный advisory-лок, взятый на одном
бэкенде и отпущенный на другом, не отпущен вовсе, а `SET` не доезжает до
оператора, которому был нужен. Другие два входа — `FromConn` и `FromDSN`.

Построенный так `Migrator` физически не может стереть схему или откатить
миграцию: для этого нужны `WithAllowWipe` и `WithAllowDown`, которые приложению
передавать незачем.

Рабочий пример — `examples/embed`.

## Файлы миграций

`<версия>_<имя>.up.sql` и парный `.down.sql`. Версия — число, имя — lower snake,
расширение в нижнем регистре: `.UP.SQL` работает на регистронезависимой ФС и
исчезает внутри `embed.FS` — самая дорогая форма отказа.

Миграция без down-файла допустима. О ней сообщает `validate`, а отказ случается
только тогда, когда откат именно её действительно запрошен.

### Директивы

Строки в шапке файла, выше любого SQL:

```sql
-- migrator:no-transaction        -- нужна для CREATE INDEX CONCURRENTLY
-- migrator:retry-safe            -- идемпотентна, можно перезапустить после сбоя
-- migrator:statement-timeout 30m
-- migrator:lock-timeout 5s
-- migrator:tags ddl,slow
-- migrator:lock-acknowledged access-exclusive
```

Неизвестная директива — ошибка, а не предупреждение: опечатка
`no-transacton` оставляет `CREATE INDEX CONCURRENTLY` внутри транзакции, где он
в лучшем случае падает с SQLSTATE 25001, а в худшем держит блокировку всю
миграцию.

## Команды

| Команда | Что делает |
|---|---|
| `up` | накатить ожидающие; `--to`, `--steps`, `--dry-run`, `--max-lock-level` |
| `down` | откатить; нужен `--allow-down`, запрещён в production |
| `redo` | откатить и накатить заново, под одним локом |
| `status` | что применено и что ждёт; `--check` для CI, `--current` для скриптов |
| `validate` | все проблемы разом; `--strict`, `--offline` |
| `create` | создать пару файлов; БД не нужна |
| `adopt` | принять существующую базу: записать применённое, ничего не выполняя |
| `repair` | починить журнал, не трогая схему |
| `wipe` | снести всё в схеме; трое независимых ворот |
| `locks` | кто держит лок миграций и как долго |
| `config` | разрешённая конфигурация и происхождение каждого значения |
| `version` | версия бинарника |

`fresh` из v1 удалена. Это был `Drop()` плюс `Up()` без подтверждения и без
представления о том, на какую базу он смотрит, — две разные вещи под одним
словом. Удобство теперь `redo`; сила — `migrator wipe && migrator up`, две
команды намеренно.

## Конфигурация

От высшего приоритета к низшему: явно набранный флаг, затем `MIGRATOR_*`, затем
`DATABASE_URL` и `PG*` из libpq, затем `.env`-файлы из `--env-file`, затем
`./.env`, затем встроенное значение по умолчанию.

Полная таблица переменных — в [английской версии](Readme.md#configuration).

У `--allow-down`, `--allow-wipe` и `--confirm` переменных окружения нет
намеренно: переменная наследуется каждым процессом в контейнере и каждым шагом
CI-джобы, а флаг набирается для одного запуска.

Пустой DSN — не ошибка: pgx тогда читает `PGHOST`, `PGUSER`, `PGDATABASE` и
`~/.pgpass`, поэтому ненастроенный `migrator` подключается ровно туда же, куда
`psql` без аргументов.

## Коды возврата

| Код | Значение | Что делать |
|---|---|---|
| 0 | сделано или нечего делать | — |
| 1 | прогон упал | читать ошибку |
| 2 | команда не понята | править вызов |
| 3 | есть непринятые миграции (`status --check`) | деплоить |
| 4 | файлы и журнал разошлись | нужен человек |
| 5 | лок держит другой migrator | повторить |
| 6 | отклонено защитой | править pipeline, а не базу |

Различие 5 и 1 — весь смысл: в CI правильная реакция на «лок держит соседний
деплой» — подождать минуту, а на «SQL неверен» — нет.
